Reverse engineering OpenSky flights — 2024-06-01

The observed table is much closer to the supplied legacy R algorithm than to a literal implementation of the 2021 description. The core split rule, timestamp convention, duration cutoff and airport distance rules are supported directly by the data. The supplied artifacts are an inferred reconstruction, not a recovered copy of OpenSky’s production source.

Study inputs: 115,699 flights from 41,497 aircraft; 72 hourly raw files for May 31–June 2, containing 2,108,598,395 state snapshots (52.50 GB compressed). Full trajectories are evaluated for a deterministic SHA-256 sample of 512 aircraft drawn from the target flight table. This positive-aircraft sample does not measure false positives among aircraft absent from that table. Endpoint probes cover every target record for which a timestamp is supplied. This report currently includes 72 extracted hours and 72 hours in the segmentation run.

The paper comparison uses the supplied excerpt and Strohmeier et al. (2021), section 3.2. Differences may reflect a different dataset/export or later implementation changes; these observations alone do not date the changes.

Every one of the 115,557 non-null starts and 115,699 ends maps to a fresh, valid supplied state with the same floored position-update timestamp. Usually this is the following snapshot; exact-integer updates can use the snapshot at the endpoint itself. In the aircraft sample, all 2,863 supplied endpoints fall in bins containing at least four fresh valid positions; 261 occur in bins containing exactly four. This is direct support for the legacy sparse-bin filter.

The supplied R files are exploratory scripts with January 2018 examples; the companion file plots results from a separate Spark implementation. They do not contain the complete production flight-table writer. Their median-speed split and quality filters are useful evidence, while the R airport routine uses three-dimensional nearest neighbors and arrival inheritance. Those details should not be copied unchanged into a 2024 reconstruction.

Executable reconstruction and remaining uncertainty

  1. Group snapshots by aircraft and sort chronologically. Require finite latitude, longitude, barometric altitude and position-update time; keep newly updated positions with time - lastposupdate < 1. Use lastposupdate as the high-resolution clock. The sampled implementation that retains valid positions despite the aggregate onground flag performs better than excluding all ground-flagged rows.
  2. Process daily batches, prepending an unfinished track from the preceding day. Remove sparse data in UTC/epoch-aligned 30-second bins with at most three fresh samples. Apply seven-point centered median checks, rejecting altitude deviations above 50 m and coordinate deviations above 0.5 degrees. The best tested window convention removes the first three and last six samples of the dense batch, before rejecting median outliers. This boundary behavior is inferred from agreement, rather than present verbatim in the R script.
  3. Calculate v[i] = haversine(position[i-1], position[i]) / (t[i]-t[i-1]). Split only when t[i]-t[i-1] > 600 and v[i] < median(v)/4. The median is derived from consecutive observed positions, not simply the reported velocity field. Median aggregation scope matters for borderline cases.
  4. Use retained segment endpoints for firstseen and lastseen, converted to integer seconds. Reject reported durations of 600 seconds or less in the current replica. All non-null durations in the supplied reference exceed 600 seconds. Reported consecutive-flight gaps of exactly 600 seconds can arise from fractional gaps above 600.
  5. Finalize segments followed by a detected landing gap. For the last segment of a batch, the tested legacy closure rule requires more than 600 seconds between its final position and midnight, and altitude within 2,500 m of the nearest airport elevation. Otherwise retain it for another daily batch, including short pending segments that have not yet reached the minimum duration. The hypothesis table compares carrying filtered positions with retaining input positions at the unfinished tail. Closure depends on the airport catalog, so it remains less certain than the split rule.
  6. Find eligible airports using the asymmetric horizontal and vertical limits above, then choose the minimum horizontal distance. Vertical distance is the absolute difference between barometric altitude and airport elevation in metres, not a universal 2,500 m ceiling above sea level. Candidate counts exclude the selected airport. Integer distance fields are consistent with truncation.
  7. Use the most frequent non-null callsign among retained positions, preserving its whitespace. Select records by UTC day of lastseen. The exact historical airport catalog, null-start handling, callsign ties and remaining batch-edge behavior are not uniquely determined by the supplied data.

Best tested model: daily_replay_emptyTrue_trimBeforeTrue_rawCarry. It exactly matches both timestamps for 1,424/1,431 reference records (99.51%) and matches both within 30 seconds for 1,431/1,431 (100.00%). It emits 1,431 records in the comparison window. These are exploratory agreement metrics on the same aircraft sample used to select hypotheses, not held-out segmentation validation or detection accuracy against independent ground truth. A tolerance match requires both endpoints to match the same reference flight. Three days of input do not reproduce any unfinished state inherited before May 31.

The separate gap diagnostic labels 6,034 gaps above 30 seconds using reference interval membership with a 30-second endpoint tolerance. A June 1 aircraft median classifies 6,033 correctly, including 1,462/1,463 gaps over 600 seconds. This conditional diagnostic excludes gaps that cannot be assigned to reference flights; its accuracy must not be confused with full reconstruction accuracy. The daily replay instead calculates its median over the current batch and pending track.

The best model retains the pending segment's input positions from its retained start onward, including the trailing samples needed for the next batch's median window. It reruns the daily filters even when a later day has no new positions. Permanently discarding the pending tail reduces exact timestamp agreement. Airport geometry and source limitations

Airport coordinates were calibrated using flight IDs whose remainder modulo 3 is nonzero, and evaluated on the remaining flight IDs. This diagnostic uses reference labels for calibration; it is not an independent airport database. Across 1,922 airports and 57,511 held-out observations, 57,389 (99.79%) direct horizontal distances agree within 2 m. The concentration of residuals between 0 and 1 m supports integer truncation. Using unmodified OurAirports coordinates leaves larger errors where metadata have changed.

The local OurAirports history supplies an as-of-2024-06-01 catalog; a pinned 2022 snapshot is also tested. Neither is asserted to be OpenSky’s private historical catalog. Current catalog type and code filters can change candidate counts even when the distance rule is correct. With small, medium and large airports having GPS codes and elevations, the following assignment results use the reference endpoints; they isolate airport rules from segmentation error and include null-to-null matches:

Metre-scale agreement supports direct endpoint distances, without requiring trajectory extrapolation. It does not uniquely establish the exact Earth radius or distinguish surface arcs from horizontal chords at every observed distance.

The provided file omits track. All 741,362 alternate-candidate airport-code slots are null, although their distances remain available. There are 142 null firstseen values. Therefore alternate-candidate identities, those start times and some production processing details cannot be recovered exactly from these artifacts alone.
